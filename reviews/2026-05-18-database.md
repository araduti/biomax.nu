# Database Review — biomax.nu

- **Agent:** database-administrator
- **Date:** 2026-05-18 · **Commit:** 2fb7538 · **Mode:** read-only (SELECT/EXPLAIN only)

## Summary

Well-designed Prisma 7 + PostgreSQL schema for current scale (20 products dev, 32 clean migrations / 8 days). Properly normalised, money as `NUMERIC(10,2)` throughout, deliberate cascade semantics, clean migration history (no rollbacks/dirty states). Main risks are forward-looking: cron query paths lack compound indexes they'll need as orders grow, two telemetry tables have no retention, and `User.role` is free-text not an enum (the one genuine normalization gap, with security implications).

## Strengths

- All monetary columns `NUMERIC(10,2)`, no `FLOAT` anywhere. Decimal→float only at integration boundaries (PostNord/Klarna/loyalty).
- Cascades chosen carefully: `Cascade` only where child is meaningless without parent; order-adjacent tables `SetNull` to preserve history.
- Append-only loyalty ledger (`LoyaltyAccount` cache + `LoyaltyTransaction` source of truth).
- Idempotency: `paymentReference @unique`, `trackingToken`/`recoveryToken`/`unsubscribeToken @unique` indexed.
- Clean migration history (all `finished_at` set, no rollbacks).
- `lib/prisma.ts` mtime proxy understood correctly — 1s throttle, disconnect-before-replace, prod-inert.

## Findings

### Critical
None — no data-corruption paths, no missing FKs on active joins, no float money.

### High
- **H1 — `Order` no `(status, reviewRequestSentAt)` index.** EXPLAIN: `Seq Scan on "Order" … reviewRequestSentAt IS NULL AND status='FULFILLED'`. Slow per cron tick at 6,000+ historical orders. Add `@@index` or partial index.
- **H2 — `OrderItem.replenishmentSentAt` no index.** `Seq Scan … replenishmentSentAt IS NULL` every replenishment cron. Add `@@index([replenishmentSentAt])`.
- **H3 — `User.role` is `String @default("customer")`** (`schema.prisma:37`), no DB constraint; a casing typo silently grants/denies admin. Introduce `UserRole` enum (CUSTOMER/ADMIN).

### Medium
- **M1** — `Session.token` has redundant plain index alongside the unique — drop `@@index([token])` (write amplification).
- **M2** — `Product.status` no standalone index (`schema.prisma:151`) — add `@@index([status, updatedAt])` (covers admin list + storefront filter).
- **M3** — `WebVital` (6,601 rows / 7 days → ~340k/yr) and `GscSnapshot` have no TTL/archival. Add nightly cleanup cron (WebVital >90d, GscSnapshot >13mo) or partition.
- **M4** — `NewsletterSubscriber` no `(welcomeSeriesStage, unsubscribedAt)` index — welcome-series cron seq-scans.
- **M5** — `BlogPost` no `(isPublished, publishedAt)` index — public listing seq-scans as content grows.

### Low
- **L1** `Verification.expiresAt` unindexed (Better Auth purge seq-scan).
- **L2** `ProductCrossSell` no `targetProductId` index (reverse `recommendedBy` seq-scan).
- **L3** `LoyaltyTransaction` lacks DB-level idempotent-earn guard — add partial `UNIQUE (accountId, orderId) WHERE kind='EARN_ORDER'` (raw SQL migration).
- **L4** `Coupon` no `(active, expiresAt)` index / no expiry pruning.

## Project Direction

Well-positioned: subscriptions schema-ready, loyalty correctly append-only, variants/bundles/cross-sells first-class, `SiteSetting` KV avoids editorial migrations, `HomepageHero` decouples seasonal content. Three pre-scale attentions: (1) **Search** — `lib/search/query.ts` uses ILIKE w/o pg_trgm, flags 500-product threshold; add pg_trgm GIN proactively. (2) **Observability growth** — WebVital becomes largest table within 6 months without retention. (3) **Role security** — free-text `User.role` is the normalization gap with security impact.

## Top 3 Priorities

1. Add `@@index([status, reviewRequestSentAt])` to `Order` (H1) — hottest cron path.
2. Migrate `User.role` → `UserRole` enum (H3) — real security surface today.
3. Add retention cron for `WebVital` (M3) — before production traffic amplifies inserts.
